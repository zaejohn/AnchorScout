# Next.js Full-Stack Application Rules

These instructions add to the repository root `AGENTS.md` and apply to the `web/` application.

## Fixed stack
- Next.js App Router only; do not introduce Pages Router.
- TypeScript with strict typing.
- Tailwind CSS for styling.
- Next.js is both frontend and backend unless `ARCHITECTURE.md` explicitly justifies an external service.
- Prefer current stable framework APIs and the version-matched Next.js docs bundled/generated by the scaffold.

## Server/client boundary
- Server Components are the default. Add `"use client"` only when browser interactivity, browser-only APIs, or client state requires it.
- Keep secrets, privileged Stellar operations, database access, and server-only SDK usage behind the server boundary.
- Do not make a component client-side merely to simplify data fetching.
- Keep Client Components small and push serializable data into them from Server Components.

## Backend conventions
- Prefer Server Actions for first-party UI mutations when they fit the flow.
- Prefer Route Handlers for public/programmatic HTTP APIs, webhooks, callbacks, third-party integrations, or endpoints consumed outside the React tree.
- Validate untrusted input at server boundaries.
- Authentication is not authorization: enforce authorization on every privileged server operation.
- Keep business logic in server/domain modules rather than duplicating it across pages, actions, and handlers.
- Make webhook and retry-sensitive operations idempotent.

## Suggested source boundaries
Use these as defaults, not mandatory empty folders:
- `src/app/` — routes, layouts, pages, loading/error boundaries, route handlers.
- `src/components/` — reusable presentation and interactive UI.
- `src/actions/` — reusable Server Actions when actions outgrow route-local placement.
- `src/lib/server/` — server-only services, repositories, auth helpers, provider clients.
- `src/lib/stellar/` — wallet/transaction helpers and generated contract client adapters.
- `src/lib/validation/` — shared boundary schemas.
- `src/types/` — shared domain types only when they do not belong next to their feature.

Prefer feature-local code over creating layers with one file each.

## Stellar integration
- Prefer generated TypeScript bindings for contract calls.
- Keep blockchain/provider logic outside presentation-only components.
- Never put secret signing material in browser code.
- Verify the active network before signatures/transactions.
- Model transaction states explicitly: preparing, awaiting signature, submitted, confirmed, failed, rejected.
- Do not treat `submitted` as `confirmed`.
- Handle disconnected wallet, wrong network, rejected signature, RPC failure, and expired/stale transaction paths.
- When a backend is authoritative for business state, do not duplicate authority in the client.

## UI and Tailwind
- Build responsive, accessible UI from the beginning rather than adding mobile support at the end.
- Prefer semantic HTML and visible focus states.
- Use Tailwind utilities and shared design tokens/components instead of large ad-hoc CSS files.
- Avoid unnecessary animation, giant client bundles, and generic dashboard-looking UI unless the product calls for it.

## Verification
For meaningful web changes, run the available commands for:
- lint
- typecheck
- tests
- production build

For user-facing flows, verify the real browser path and inspect server/browser errors. For Stellar flows, verify local/testnet outcomes as required by the root instructions.
